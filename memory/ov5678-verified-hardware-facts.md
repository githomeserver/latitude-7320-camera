TPS68470 PMIC = `INT3472:07` = `\_SB.PC00.CLP0`, `_DDN "PMIC-CRDG"`, i2c 0x4d on I2C2. CLDB: version 1, `control_logic_type` 2 (TPS68470), `control_logic_id` **0** (offset 0x02 is never written by the DSDT, so it is statically zero), sku 0x50. `C0W0..C0W5` live at CLDB offsets **0x08–0x0D**: `C0W0`=14, `C0W4`=3, rest 0. Note 14 is out of range for tps68470-gpio (pins 0–9), so these are not straightforwardly TPS68470 pin numbers.

**How to read the module EEPROM at 0x51 (done 2026-08-15, `tools/read-eeprom.sh`).** Three things make it work:
- **The rails must be up.** The EEPROM is on the camera module and shares the sensor's supplies, so a cold `i2cdetect` gives controller timeouts. Hold a capture open (the script reads `/dev/video0`) and verify VSIO/AUX1/AUX2 all read `enabled` before touching the bus. Charles established that all three must be on together for the bus to respond at all.
- **It is 16-bit addressed.** An 8-bit addressed read returns `0xff` everywhere, while a pure read with no address written returns real data — the two disagree, which is the signature of a 16-bit part.
- **Derive the bus, do not scrape digits.** The front sensor is on i2c-1, the rear on i2c-2. Take the bus from the parent directory of `/sys/bus/i2c/devices/i2c-OVTI5678:00` (`.../i2c-1/...` → 1). A `grep -oE '[0-9]+'` over the full sysfs path returns **2**, because the string "i2c" contains a 2 — that would have pointed every read at the rear module.

**The write hazard, and the trick that removes it.** Reading needs an address pointer written first. Sending two address bytes to an *8-bit* part makes the second byte DATA — a write, onto irreplaceable factory calibration. Sending one byte to a 16-bit part is harmless. So probe 8-bit first, and make the first 16-bit probe **idempotent**: send `[0x00][0xff]` rather than `[0x00][0x00]`, because the 8-bit probe already showed offset `0x00` reads as `0xff`, so under the dangerous hypothesis the write is a no-op. `[0x00][0x00]` is the one combination that damages an 8-bit part.

Two gotchas that cost real time:
- **`acpi_call` truncates its /proc reply at 256 chars**, i.e. ~42 bytes of buffer. CLDB (32 B) survives; SSDB (108 B) is silently cut at offset 0x29, losing MCLK and control-logic-id. Read the root-scope NVS scalars individually instead.
- The brief's "worked example" values (link 0, 4 lanes, 24 MHz) come from the **disabled** `CAM0` DSDT branch and are wrong for live hardware.

`LNK0`/`LNK1` `_DEP` returns `CLP0` (via `CDEP`, because `C0TP` > 1). So the sensor i²c clients `i2c-OVTI5678:00` / `i2c-OVTI8856:00` are **not created at all** until the INT3472 driver probes successfully and calls `acpi_dev_clear_dependencies()`. That makes "do those nodes appear?" a Phase A success test needing no IPU6.

**THE KEY FINDING (2026-08-08): the "OV5678" reports chip id 0x005675 — it is an OV5675.** Read over i2c at 0x300a–0x300c = `00 56 75` (0x302a = 0xb0) once powered correctly. Mainline `ov5675.c` matches on every independent parameter: `OV5675_CHIP_ID 0x5675` at `0x300a`, `OV5675_DATA_LANES 2` (our `L0NL`=2), `OV5675_XVCLK_19_2` (our `L0CK`=19.2 MHz), and 2592×1944 ≈ 5 MP. So **Phase D (register-sequence reverse engineering, the "project may fail here" phase) is almost certainly unnecessary** — reuse `ov5675.c` by adding `OVTI5678` to its ACPI match table. Phase B link frequency = `OV5675_LINK_FREQ_450MHZ` = 450000000.

**CONFIRMED ON THE REFURB, 2026-08-14 — the whole stack works on a second physical unit.** Fresh Ubuntu install, DKMS `camera-dell7320/0.3`, `rail_map=1` and **no GPIO pin assigned at all**: INT3472 binds, 7 rails register, both `i2c-OVTI5678:00` and `i2c-OVTI8856:00` appear, ipu-bridge reports `Connected 2 cameras`, `ov5675 1-0036` is in the media graph, and libcamera lists "Internal front camera (\_SB_.PC00.LNK0)". So the DMI match, the `_DEP` clearing and patches 2/3 and 3/3 **generalise across units** — they are no longer one-machine results.

**`rail_map=1` is REQUIRED, and this is evidence the rail assignment is not cosmetic (2026-08-14).** Provisioning the refurb with `rail_map` left at its compiled-in default of 0 (the "conventional" ANA/CORE/VSIO mapping) made the sensor fail to identify: `ov5675 i2c-OVTI5678:00: failed to find sensor: -5` at boot and on every reload. Setting `rail_map=1` (VSIO/AUX1/AUX2, the Dell 7212 prior art, which is also what the sent patch 1/3 actually ships) fixed it outright with nothing else changed. **CORRECTION 2026-08-15 — this does NOT contradict Charles, it confirms him.** An earlier version of this note claimed the result disproved his "the mapping has no impact" position. It does not, and the distinction matters. His claim is that *permuting the avdd/dvdd/dovdd labels among a fixed set of rails* has no effect, because all of the sensor's supplies are enabled and disabled together — which is true. Our experiment changed the **set of rails** (rail_map=0 puts the consumers on CORE/ANA/VSIO; rail_map=1 puts them on VSIO/AUX1/AUX2), not the labelling within a set. Mechanism: `regulator_bulk_enable` only enables rails that carry consumers, so under rail_map=0 the AUX1/AUX2 rails the front module actually needs are never switched on and the sensor is unpowered. Charles independently reports the front OVTI5678 probing on VSIO/AUX1/AUX2 (his AUX2 at 1.2132 V, ours at 1.8006 V — both work), and says CORE/ANA/VSIO is the correct set for the *rear* OVTI8856. So the finding is: **the front module's supplies hang off VSIO/AUX1/AUX2 and those rails must be enabled** — independent support for his arrangement. Which of the three is avdd remains untestable from here; his datasheet-current argument (AUX1 max 150 mA is closest to ANA's 200 mA, AUX2 only 80 mA, and Surface Go mappings agree) is the best inference available and points at AUX1→avdd, where the sent patch has VSIO→avdd.

**Trap for anyone re-provisioning:** the module's default is `rail_map=0`, so omitting the option from `/etc/modprobe.d/int3472-dell7320.conf` silently selects the deprecated mapping and looks like dead hardware. `tools/provision-machine.sh` now sets it explicitly with a comment saying why.

**Working power configuration**: `front_reset=3 front_powerdown=4 rail_map=1 rear_reset=-1 rear_powerdown=-1` via `/etc/modprobe.d/int3472-dell7320.conf`. **This was called "proven" and it is not — 2026-08-10 correction.** It proves the sensor works, not that the mapping is right. Charles Drolet (`cdrolet64`, GitHub issue #1), who has a 7320 Detachable, shows the front sensor probes with **no pin assignment at all**, so a wrong mapping is invisible:

- **There is no powerdown pin, provable from source**: mainline `ov5675.c` requests only `"reset"` (`devm_gpiod_get_optional(dev, "reset", ...)`, ~line 1205). No `"powerdown"` con_id exists in that driver, so the `GPIO_LOOKUP(..., 4, "powerdown", ...)` in the sent patch is dead code, never looked up. Certain, no hardware needed.
- **Reading Charles's gpioset logs: mind the `-l`.** His commands are `gpioset -l -m wait gpiochip1 5=1` → probe **fails**, `5=0` → probe **succeeds**, which looks like it inverts this note. It does not. `-l` is `--active-low`, so logical `1` drives the pin **physically low** and `0` drives it **high**. Physically low = held in reset = fails. Consistent with everything below. Also note **libgpiod 2.2 (on the refurb) dropped `-m wait` and needs `-c <chip>`** for numeric offsets — his invocation will not run verbatim. And never trust `gpiochip1`: find the chip by its `tps68470` label, since numbering follows probe order.
- **THE v2 SHIPPING CONFIG IS VALIDATED ON HARDWARE, 2026-08-14.** Booted with `front_reset=5 front_powerdown=-1 rail_map=1 rear_reset=-1 rear_powerdown=-1` — exactly what v2 of patch 1/3 will contain. `check-camera.sh` fully passes (sensor bound, `ov5675 1-0036` in the graph, libcamera enumerates the front camera), and the suspend test is clean in this configuration too (SILENT trace, no refcount change, camera survives). So assigning the correct reset does not break the camera that worked unassigned. **The lookup demonstrably resolves:** with `front_reset=5`, `gpioset` on line 5 returns `Device or resource busy` while line 3 stays freely drivable — the driver is holding line 5. Contrast the old `powerdown` lookup, which claimed nothing because `ov5675.c` never requests that con_id.
- **Verbatim kernel-side proof for the v2 commit message** (`gpioinfo -c gpiochip1`, front_reset=5): `line   5:       "gpio.5"                output active-low consumer="reset"` — the only claimed line on the chip. The full 10-line listing also names **line 7 `s_enable`, line 8 `s_idle`, line 9 `s_resetn`**, confirming those are the SGPO-backed specials the notes warn about and fitting Charles's use of 9 as the rear reset; and shows **line 3 as an output with no consumer**, i.e. driven but wired to nothing relevant, which is the physical picture behind "inert". Lines 0/1/2/4/6 are inputs.
- **`gpioinfo` output format differs by libgpiod major version** — v1 prints `[used]`, v2 prints `consumer="..."`. A check grepping only for `used` silently reports "no lines claimed" on v2 even when a driver holds the line, which is how the assigned-config branch of `test-gpio-mapping.sh` failed to trigger the first time. Grep for both.
- **REPRODUCED INDEPENDENTLY ON THE REFURB, 2026-08-14 — this is now a two-unit result and 1/3 v2 is unblocked on the GPIO question.** `tools/test-gpio-mapping.sh`, 3 trials per condition, against a build with no pin assignment: line 5 physically **low fails 3/3** (`failed to find sensor: -5`, distinct kernel timestamps each trial, so the reload really cycled), line 5 **high probes 3/3**, line 3 **low probes 3/3**, line 3 **high probes 3/3**, and the sensor probes with nothing driven. So reset is line 5, active low; line 3 is inert; and a wrong mapping is invisible on this unit too. **Instrumentation trap that nearly produced a false pass:** the first version printed `dmesg | tail -3`, which showed identical stale lines for every condition — indistinguishable from a harness where `modprobe -r` had silently failed and left the driver bound. The fix is to assert the unload happened (`lsmod` + sysfs link gone) and `dmesg -C` before each reload, so a *silent* buffer is the success signal; a stock `ov5675` logs nothing when it identifies.
- **Reset is tps68470-gpio 5, not 3 — established, not merely reported (2026-08-12).** Held with `gpioset -l -m wait gpiochip1 5=…` against a build with no pin assignment (so no driver contention): pin physically low → `failed to find sensor: -5`; physically high → identifies. Active low, matching `GPIO_ACTIVE_LOW`. Line 5 sits released by default, which is why 3/4 appeared to work. **Charles ran the control test: pin 3 has no effect on probing at all**, so 3 was never a worse guess — it is wired to nothing relevant. Rear OVTI8856 reset is pin **9**.
- Rail map is **disputed and unresolved**: this note has avdd←VSIO 1.8006 V, dvdd←AUX1 1.2132 V; Charles has avdd←AUX1 **2.8152 V**, dvdd←VSIO 1.8006 V. The ov5675 wants ~2.8 V analogue so his is datasheet-plausible, yet both work — supporting his theory that these TPS68470 rails are enables for downstream regulators, not the supplies. Unsettleable without measuring the rails.

He independently corroborates the ACPI reading: VCM rear-only, EEPROM at 0x51 on both busses, identical `IPU_SENSOR_CONFIG("OVTI5678", 1, 450000000)`. His weakest claim, hedged "I think", is rear reset on **gpio 9** — the `S_RESET` line this note warns wedges the PMIC when driven. Unconfirmed.

**CCM: attempted and abandoned, deliberately (2026-08-08).** Do not retry without new information. Red and green rows fit cleanly (~1.5 diagonal, modest negative off-diagonals) but the blue row is unfittable: the camera's blue output is anti-correlated with subject blueness — a yellow patch (target B=31) reads camera B=236, higher than a blue-flower patch (target B=177, camera B=181). Target blue spans 6x, camera blue only 2.4x. With native B/G 0.163 and a 4.9x AWB gain, blue is dominated by crosstalk and flare rather than blue light, so there is no relationship to fit. Excluding shadow-corrupted darks made the blue row worse (-0.08 → -0.43), confirming it is not a shadow-offset problem. Tools kept at `tools/solve-ccm.py`, `tools/make-ccm-target.py`.

**THE CFA PHASE IS GBRG, NOT GRBG (2026-08-08).** `ov5675.c` hardcodes `MEDIA_BUS_FMT_SGRBG10_1X10` in three places, but on this board red and blue are transposed — consistent with the module being mounted 180° (rotating GRBG by 180° gives GBRG). Proven by capturing one raw frame and demosaicing it both ways (`tools/demosaic-both-ways.sh`): a known-red Kmart logo renders red under GBRG, blue under GRBG. Confirmed after patching: AWB gains mirrored (red 6.01→1.46, blue 1.54→4.90) and the estimated colour temperature went 6752 K → **3139 K**, i.e. from implausible daylight to correct warm-indoor.

**Beware: the green-diagonal test cannot detect this.** GRBG and GBRG both put greens at (0,0)/(1,1), so "the two greens agree" rules out RGGB/BGGR only. An R/B swap is also invisible to grey-world AWB, since balancing to neutral grey works whichever way the channels are labelled — greys look right while all colours are wrong.

**Not upstreamable as-is:** changing the mbus code unconditionally would break every ov5675 mounted the other way up; it needs a board-specific key. Separately, `ov5675.c` never adjusts the mbus code when H/V flip are applied, which is a real latent bug worth reporting.

**Colour: three libcamera 0.7.0 bugs, all needed fixing (2026-08-08).** On lit white paper, linear R/G went 0.372 → 1.091 and saturation 34% → 5.1%:
1. **AWB gain clamp.** `src/ipa/simple/algorithms/awb.cpp` hardcodes a 4.0 ceiling (`sum.r() <= sum.g()/4 ? 4.0f : ...`). This sensor needs 6.1, so red was pinned at exactly 4 on every frame. Patch removes the ceiling, matching libipa's `AwbGrey` on master. → `libcamera-patch/`
2. **Black level guessed from the scene.** With no tuning file, `BlackLevel` estimates the pedestal from the 2nd percentile of the luminance histogram, and `Awb::calculateRgbMeans()` subtracts that guess. Pinning `blackLevel: 4122` (64.4 in 10-bit ×64; `>>8` = 16) took the computed red gain from 4.79 to **6.01** vs 6.13 predicted. → `libcamera/ov5675.yaml`
3. **The GPU debayer does not apply the gains.** `debayer_egl.cpp`'s shader has no gains uniform (only `ccm`, `blacklevel`, `gamma`, `contrastExp`), so gains must be folded into `params.combinedMatrix` — and evidently are not, correctly. Same scene: GPU R/G 0.552, CPU R/G 1.091. Workaround `LIBCAMERA_SOFTISP_MODE=cpu`. → `tools/try-cpu-isp.sh`

**Cost of the CPU debayer:** relay CPU 36% → 45%, fps measured 28 and 17.6 on two consecutive runs (unresolved variance; beware leftover gst processes contending for the camera).

**Colour / AWB earlier measurements (2026-08-08, well-lit white paper, all ratios in LINEAR light):** sensor native, black-level corrected, is **R/G 0.164, B/G 0.665** (black level ≈ 64.4 in 10-bit; measure it as a dark frame at min exposure+gain and subtract, or the pedestal dominates and the ratios look far closer to neutral than they are). After the soft ISP: **R/G 0.391, B/G 0.938** — so AWB applies red ×2.38 where ×6.1 is needed. `AwbEnable=false` gives identical output, and `ColourGains` is ignored across a 2→8 red sweep. Green cast is therefore a libcamera soft-ISP AWB defect, **not** a missing CCM or tuning file, and **not** fixable via `libcamerasrc` properties. Report drafted at `upstream-libcamera/AWB-BUG-REPORT.md`.

**Measured sensor delays (2026-08-08):** exposure, analogue_gain and vblank all **2 frames** (8/9, 9/9, 9/9 run agreement). Measured with `tools/measure-sensor-delays.sh` — raw Bayer straight off `/dev/video49` via V4L2, bypassing libcamera (which would be circular). `V4L2_CID_HBLANK` is **read-only** on this sensor (min=max=1704) so its delay is unobservable. Frame-timing cross-check confirms the chain: HTS = 1296+1704 = 3000 at 180 MHz → 16.67 µs/line, so 2020 lines = 33.7 ms and 5164 lines = 86.1 ms, vs 33.4 / 85.1 measured.

**Prior art for the GPIO/rail mapping** (the part ACPI does not give you): the Dell Latitude 5290 2-in-1 out-of-tree fix (`jelsco/latitude-5290-camera`) reuses the in-tree Dell 7212 configuration verbatim — **reset = tps68470-gpio pin 3 (active low), powerdown = pin 4 (active low), VSIO→avdd, AUX1→dvdd (1.2132 V), AUX2→dovdd (1.8006 V)**. Two independent Dell TPS68470 tablets agree, and `C0W4`=3 in this machine's CLDB corroborates reset=3. Prefer this over the "conventional" ANA/CORE/VSIO mapping. The brief's cited "Thierry Chatard, March 2026, Latitude 5285" LKML series could not be found in search — treat that reference as unverified.

**DOES NOT REPRODUCE ON THE REFURB, 2026-08-15 — do not repeat this warning upstream as established fact.** `tools/test-sgpo-lines.sh` drove **all three lines at both polarities, six combinations**, each followed by a full health check (rail states readable *and* a real camera open, which is what calls `regulator_bulk_enable` — the call that originally failed `-EREMOTEIO`). Every one stayed healthy. This matches Charles, who drives these lines freely on the same model and uses 9 as the rear reset.

**Say it no more strongly than "does not reproduce here".** Why the original observation happened is unknown — it was a different physical unit, and the rail and driver state at the time were never recorded. **Do not attribute it to `rail_map` or any other cause**; an earlier draft of the test script asserted a rail-configuration explanation with no evidence for it, which is the same error as the retracted EGL mechanism. The original was a real observation; it simply cannot be explained or reproduced now.

**Watch for a false pass if you rerun this.** The first two attempts produced confident results having driven nothing: the script named its list variable `LINES`, which is a **bash special variable (terminal height)** that bash overwrites after every external command when `checkwinsize` is on — the default since bash 5.0. It survived until the baseline health check ran `cam`, then became `61`, the terminal's row count. A local repro of the same script passed cleanly because the harness is not a tty and bash therefore never touched it. The verdict is now gated on a counter of combinations actually driven.

Original observation follows, retained because it happened. **Never drive tps68470-gpio lines 7, 8, 9** (`s_enable`, `s_idle`, `s_resetn`, backed by `TPS68470_REG_SGPO`). Doing so wedges the PMIC until a reboot: `regulator_bulk_enable` then fails `-EREMOTEIO` and every rail reads `unknown`. On this board even brute-force driving the *regular* lines 0..6 wedged it, so GPIO sweeping is not a viable discovery technique here — use prior art instead.

Only `intel_skl_int3472_tps68470` needs rebuilding (Makefile: `tps68470.o + tps68470_board_data.o`); `intel_skl_int3472_common` is a separate module exporting its symbols under namespace `INTEL_INT3472`. Matching source: `linux-source-7.0.0` 7.0.0-29.29.
